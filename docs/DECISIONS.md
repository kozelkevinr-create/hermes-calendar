# Decisions

Implementation decisions taken where the design documents leave room, one line each.
Date, decision, why.

- 2026-11-12 — Both stores use the same v1 schema and seed a local source `src_local`; only the global store seeds its one `cal_global` calendar. Why: `core.md` §5.2 requires exactly one global calendar but leaves profile calendar creation to the user, while a local source is the minimum needed for `create_calendar`.
- 2026-11-12 — Schema v1 omits `custom_timezones`, the instance cache, sync tables, FTS, and notification tables. Why: the M1 task explicitly scopes those out and they can be added by later additive migrations.
- 2026-11-12 — `create_event` takes a frozen `EventDraft`; `update_event` takes a full `Event` plus `expected_rev` and replaces mutable fields. Why: one aggregate-shaped API keeps `source_id`/`scope` consistent with the calendar and makes frozen dataclasses usable with `dataclasses.replace`.
- 2026-11-12 — `delete_event` takes an optional `expected_rev` and treats a repeat delete as a no-op. Why: the task requires CAS on update; idempotent delete is safer for retries and the row remains addressable as a tombstone.
- 2026-11-12 — `list_events` returns non-recurring rows (timed and all-day) by UTC sort keys and excludes recurring masters and overrides. Why: M1 skips recurrence expansion, and all-day rows already carry stable UTC-midnight keys.
- 2026-11-12 — A profile store's identity is its profile directory name from `profile_dir().parent.parent.name`; opening an existing store verifies its scope but not its `store_id`. Why: `core.md` §4.1 defines identity by directory name and says a rename is a store-id migration, so a hard failure on drift would block that migration.
- 2026-11-12 — Global-store events use `draft.owner_profile_id` or the write `actor` as creator; profile-store events always take the calendar owner. Why: `core.md` §4.6 requires the creating profile in the shared store, while profile ownership is fixed by the store.
- 2026-11-12 — Keep the shared `plugin_storage.open_db` pragma stack, including its 5 s `busy_timeout`, rather than overriding it to the design's 10 s. Why: the task requires that helper to own connection setup, and M1 write transactions are short; the helper remains the one place to tune it.
- 2026-11-12 — Use `python-dateutil>=2.9` for the RFC 5545 grammar instead of a hand-rolled parser; it is pure Python and already present in the Hermes runtime (2.9.0.post0 in the installed environments), and the design explicitly asks for a vetted library (§6.2).
- 2026-11-12 — Give `hermes_calendar.recurrence` explicit `MasterEvent`/`OverrideEvent` dataclasses rather than accepting SQLite rows; this keeps the module pure, typed, and free of database imports, with mapping left to the storage layer.
- 2026-11-12 — Resolve floating timed events in UTC during expansion; `expand()` has no calendar default zone, so this preserves the wall clock without inventing a caller-specific zone. Callers that have a calendar zone pass it as `start_tz`.
- 2026-11-12 — Expand an RRULE-less master as `{DTSTART} ∪ RDATE − EXDATE` rather than returning only the master; this follows the normative recurrence-set definition in §6.1 and makes RDATE-only series work.
- 2026-11-12 — Filter all-day occurrences by the UTC dates of the supplied window; this matches the date-based query in §6.8 and keeps all-day dates free of time-zone shifts.
- 2026-11-12 — Accept UTC window bounds as either timezone-aware datetimes or epoch seconds; epoch seconds are what SQLite stores, and normalizing once at the public boundary keeps the rest of the engine in datetimes.
- 2026-11-12 — Apply overrides only to occurrences the RRULE/RDATE window generated; an override moved into the window from an original occurrence after the window is not discovered, which avoids scanning an unbounded future for a rare case.
- 2026-11-12 — Tool datetimes without an offset default to `HERMES_TIMEZONE`, then the profile `config.yaml` top-level `timezone` key, then UTC; the tool also accepts an explicit `timezone` argument. Why: Hermes resolves the same order, but importing its private clock module would break the plugin contract, and reading one top-level YAML key keeps the plugin dependency-free.
- 2026-11-12 — Implement `hermes_calendar/ics` with a small in-repo RFC 5545 reader/writer instead of the `icalendar` package. Why: `python3 -c "import icalendar"` fails both locally and on `docker-host` (the Hermes environment), the task allows either, and stdlib `zoneinfo` already supplies TZID/DST handling without adding a dependency.
- 2026-11-12 — Parsed drafts carry `calendar_id=""`, no `parent_id`, and `recurrence_key`/`recurrence_id_raw` on overrides; callers bind them to a calendar/series with `dataclasses.replace`. Why: the parser has no store or master-row context and must not invent identifiers.
- 2026-11-12 — `RDATE`/`EXDATE`/`RECURRENCE-ID` are normalized to ISO date or local date-time strings (`...Z` for UTC), and `PERIOD` values are reduced to their start with a warning. Why: `core.md` Appendix A requires canonical value strings but leaves their spelling open; the ISO form matches the §3.2 example.
- 2026-11-12 — Floating event times are resolved to UTC for the `start_utc`/`end_utc` sort keys, while `is_floating` and the bare wall clock are preserved. Why: a draft has no calendar `default_tz`; the caller can re-resolve the display key if its calendar zone differs.
- 2026-11-12 — `VTIMEZONE` blocks are not parsed; TZIDs are resolved through IANA `zoneinfo`, and a TZID missing from the database warns and falls back to UTC. Why: custom zones belong to the store's `custom_timezones` table, which this library-only task does not own, and silent UTC substitution is avoided.
- 2026-11-12 — Unknown `VEVENT` properties are stored in `EventDraft.xprops` as their raw unfolded content lines (a list when repeated); unknown `VCALENDAR` properties are reported as warnings. Why: `xprops` is the existing round-trip field, and `ParseResult` has no calendar-extras field to preserve the latter.
- 2026-11-12 — A `VEVENT` without `UID` gets a deterministic synthetic UID plus a warning; a timed event with neither `DTEND` nor `DURATION` ends at its start, and all-day events default to one day. Why: RFC 5545 requires `UID` and a zero-length/default range keeps malformed input usable and round-trippable without inventing wall-clock policy.
- 2026-11-12 — Documents over 5 MiB raise `IcsLimitError`; beyond 10,000 events parsing stops with one warning; component nesting is capped at 32 levels and pathological DURATION digit counts are treated as malformed. Why: the task requires rejection/truncation caps, and the extra guards keep hostile input from raising `RecursionError` or `ValueError` instead of a warning.
- 2026-11-12 — Unknown `VALARM` actions, attendee roles/partstats/CUTYPEs, and event `STATUS`/`TRANSP`/`CLASS` values fall back to the model defaults with a warning. Why: `db/schema.py` constrains those columns, so passing an unknown token through would make a later insert fail.
- 2026-11-12 — Import inside `hermes_calendar/` only relatively, and let the root `__init__.py` use an absolute fallback only when `__package__` is empty. Why: Hermes loads the plugin directory as a package without putting it on `sys.path`, while pytest collects the repository root as a package and imports its entry point as a bare module; the relative import stays the path Hermes takes. `tests/unit/test_relative_imports.py` fails if an absolute `hermes_calendar` import reappears in the package.
- 2026-11-12 — `calendar_update_event`/`calendar_delete_event` default `series_scope` to `this` when `occurrence_start` is supplied and to `all` otherwise, and `occurrence_start` is ignored when `series_scope` is `all`. Why: callers can select an instance without repeating the scope, while an explicit `all` should always win; the master row's `rev` is the single compare-and-swap token for both modes.
- 2026-11-12 — ICS import upserts masters and overrides by UID/`recurrence_key` but does not delete rows absent from the document. Why: M6 requires idempotent import without duplicates, while destructive snapshot diffs need an owning feed/mapping that this tool does not have.
- 2026-11-12 — `calendar_list_events` keeps the `recurrence_expanded` envelope key and sets it true only when the requested calendars contain a recurring master. Why: the key already existed and non-recurring listings kept their old value, while expanded listings advertise that occurrences replaced master rows.
- 2026-11-12 — Validate against the real Hermes install with `make validate-remote` (tar over ssh to `${HERMES_VALIDATE_HOST:-docker-host}`, run `hermes plugins validate --json`, delete the staging directory) instead of `HERMES_VALIDATE=1` locally. Why: the loader only exists on that host, the probe must see an installed-like directory, and the plugin must never be installed into the host's `~/.hermes/plugins`.
- 2026-11-12 — Schema v2 follows `core.md` §5.11 column-for-column for the per-profile notification tables (`reminder_instances`, `notification_deliveries`, `notification_channels`, `notification_prefs`, `web_push_subscriptions`) and keeps `app-notifications.md` §6.5's `dedup_key` as the design sketches it, so no column was renamed during reconciliation. Why: the two documents had already converged on these names; only ownership needed to be made explicit.
- 2026-11-12 — The shared global store's v2 schema gets only `reminder_lease` and the content-free `reminder_delivery_ledger`, not the notification content tables. Why: `core.md` §3.7/§5.11 say the global store has no notification state, while `app-notifications.md` §6.2 needs one mutex and one dedup ledger; classifying those two rows as coordination state resolves the TODO without duplicating delivery history.
- 2026-11-12 — Only the profile holding the global lease materializes `store_id='global'` instances; non-holders materialize nothing for global events. Why: `app-notifications.md` §6.2/§6.4 choose owner-only materialization to satisfy R8 (no duplicate delivery), superseding `core.md` §5.11's earlier "each profile materializes its own" wording and the Q23 default.
- 2026-11-12 — A successful global delivery writes the ledger row only after the final delivery outcome, not on a transient retry. Why: recording too early would block a legitimate chat retry by the next lease holder, while recording on success still prevents replay after takeover.
- 2026-11-12 — `snooze_until_utc` also stores the next retry time for `state='retrying'` rows. Why: the reconciled schema has no `next_attempt_utc` column, and the claim query already honors a not-before timestamp for both user snoozes and retry backoff.
- 2026-11-12 — Relative reminders materialize their `event_reminders.offset_seconds` (rather than `fire_at - occurrence_start`) so an all-day `-P1D` reminder still renders as "in 1 day"; absolute and `RELATED=END` triggers derive an equivalent offset from the fire instant. Why: all-day occurrences use UTC-midnight sort keys while their configured fire time is 07:00 local, and the raw VALARM offset is the user-facing lead time.
- 2026-11-12 — A `REPEAT` VALARM becomes `repeat_count + 1` instances whose recurrence keys are suffixed `#r<n>` and whose fire times advance by `repeat_interval_seconds`. Why: the schema's uniqueness is per occurrence, so repeats need distinct keys to remain addressable and idempotent.
- 2026-11-12 — Non-recurring events use the recurrence engine's own `T:<epoch>`/`D:<date>` keys for instances even though the core row stores `recurrence_key = NULL`. Why: this keeps one canonical key shape for `UNIQUE(store_id, event_id, reminder_id, recurrence_key)` and reuses the tested recurrence code path.
- 2026-11-12 — Stale suppression for timed reminders is occurrence start + `stale_grace`, except `RELATED=END` alarms use occurrence end + grace and all-day reminders use event end + grace; all-day reminders are exempt from the `max_late_minutes` fire-time rule. Why: start-based suppression would suppress a legitimate end-of-meeting alarm, and an all-day reminder is still useful after its morning fire time.
- 2026-11-12 — Quiet-hours deferral sets `snooze_until_utc` and the catch-up limit measures lateness from `max(fire_at, snooze_until)`. Why: otherwise a 22:00 normal reminder deferred to 07:00 would be suppressed as more than 60 minutes late, defeating quiet hours.
- 2026-11-12 — The catch-up "while you were away" prefix starts at 120 seconds past the effective fire time. Why: a normal one-minute cron tick is up to 60 seconds late by design and should not be labelled as catch-up.
- 2026-11-12 — The in-app record always counts as a successful channel, so a permanent chat failure or an exhausted retry budget finishes the instance as `delivered` with the failure visible in `notification_deliveries`. Why: acceptance check 8 requires fallback to in-app rather than silence, and in-app is the source-of-truth record.
- 2026-11-12 — The `hermes_send` target is read only from `notification_channels.config_json["target"]`; the migration seeds `in-app` enabled and `phone` disabled with no target. Why: task and design forbid inferring a DM or room, and `hermes send --list` must never choose a destination.
- 2026-11-12 — Chat messages contain only the sanitized summary, a relative-time phrase, and either the configured dashboard/public URL link or "Open the calendar app"; descriptions, locations, attendees, event URLs, and media are never fetched into the message. Why: `app-notifications.md` §6.10/§6.13 make location and detail opt-in, and the plugin stores no per-reminder detail flag yet.
- 2026-11-12 — Notification settings live under the `notification_prefs` key `notifications` with the YAML shape from `app-notifications.md` §6.8; `last_tick_utc` is a separate key. Why: one JSON document is easy for the future dashboard to edit, while the clock guard stays independent.
- 2026-11-12 — The optional in-process ticker is off by default and starts from `register(ctx)` only when `ctx.spawn_task` exists and `notifications.in_process_ticker.enabled` is true; it uses `asyncio.to_thread(run_tick)` and is cancelled by Hermes on unload. Why: the design calls it an accelerator, not the scheduler, and a bare import-time thread would be profile-unsafe.
- 2026-11-12 — The cron helper prints `hermes cron create` plus the script body but never creates the job. Why: jobs outlive plugins and the task requires the user to run the command deliberately.
- 2026-11-12 — `hermes_send` failures store only a generic classification and exit code, never raw stderr. Why: stderr may quote the message body or target; the delivery log is not a content store.
- 2026-11-12 — `reminders doctor` treats a missing/untargeted/targetless `hermes_send` channel and a missing `hermes` binary as essential failures (exit 1), but a missing global store only as a warning. Why: acceptance check 11 requires a non-zero exit for a broken external channel, while profile-local reminders remain useful without the shared global database.
- 2026-11-12 — Chat rendering neutralizes the three directives the installed Hermes build recognizes (`MEDIA:<path>`, `[[as_document]]`, `[[audio_as_voice]]`) by replacing the MEDIA colon with U+2236 and breaking bracket pairs, including case, whitespace, zero-width, full-width-colon, and full-width-bracket variants. Why: review showed event summaries reach `hermes send` as message text and a surviving `MEDIA:` attaches a local file; the neutralizer cites `gateway/platforms/base.py` lines 1220-1253/1312/3203-3248 and is applied in both `render.sanitize` and the adapter.
- 2026-11-12 — `hermes send` argv uses `--to=<target>` and `--subject=<subject>` single-token forms, and the message body is passed only on stdin. Why: a title beginning with `-` must not be parsed as an option, and the target remains whatever explicit channel configuration supplied, never event text.
- 2026-11-12 — User-controlled chat text replaces `/` with U+2215 and `\\` with U+29F5 so Hermes `extract_local_files` (base.py lines 3253-3281) cannot attach an existing bare local file; the operator-configured dashboard URL footer is added after sanitization and keeps normal slashes. Why: review found a second attachment path with no `MEDIA:` marker, and the exact Hermes path regex requires a literal path separator.
